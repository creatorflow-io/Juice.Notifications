# Deferred findings

Review findings that are not correctness bugs: efficiency, cleanup and operability ideas. They don't block a milestone. Larger efficiency work is
picked up in the milestone where it can be measured (M8: history, operations and host), not fixed speculatively.

| # | From | Finding | Where it goes |
|---|---|---|---|
| 1 | M1 review, round 3 | A lost race that the API answers (`application_exists`, a fresh 200, `tenant_in_use` or `concurrent_change`) still logs at Error level twice: EF Core's SaveChanges failure and Juice `TransactionBehavior`'s "ERROR Handling transaction". Log-based alerts would fire on normal traffic. Options: lower EF's `Microsoft.EntityFrameworkCore.Update` category for conflicts, and raise with Juice whether `TransactionBehavior` should log conflicts below Error. | M8 (operations): with the metrics and alert rules |
| 2 | M1 review, confirmations 3 and 4 | **Juice task: commit failures in `UnitOfWork`.** Juice 10.12.0's `UnitOfWork.CommitTransactionAsync` rolls back a transaction Npgsql already completed when `COMMIT` fails, and the rollback's "has completed" error replaces the real one, so a commit-time conflict is not recognized (500). **Fixed 12 Nov 2026 in Juice `release/10` (c68a63e), released in Juice 10.13.0:** a failed commit throws `TransactionCommitFailedException` with the provider's error as `InnerException`, so no execution strategy retries it (a retry used to commit an empty transaction and report success). Rollback errors never replace it, a failing post-commit hook or reload no longer fails a committed transaction, and the dead transaction is detached. On the bump, conflict translation must read `InnerException`. Phase 1 has no commit-time conflicts (no deferred constraints, read committed) and stays on 10.12.0. | Its own Juice task; bump `Juice.*` once released, before any deferred constraint or stricter isolation is used |
| 3 | M2 review, round 1 | ~~`HasAnchor` walks the whole schema again for every `#anchor` reference.~~ **Resolved 12 Nov 2026:** the reference check now walks the subschemas once and collects their anchors. | — |
| 4 | M2 review, round 1 | A declaration that loses the version race re-runs every check (meta-schema, build, template parses) to recompute its hash in the endpoint. Carry the hash out of the handler instead. Also: `TypeRules.Passthrough` duplicates `TemplateEngines.Passthrough`. | M8 |
| 5 | M2 review, round 1 | **Correctness, scheduled:** templates are checked with Scriban's parser at declaration, not yet with the sandbox (§8.2): `include`/`import` and non-allowlisted built-ins are only refused at render. M5 builds the sandbox; the declaration check must call it then. | M5 (p1-11) |
| 6 | M2 review, round 2 | **Hardening:** JsonSchema.Net matches each schema `pattern` with its own fixed 5 s timeout, and offers no hook to change it, so a pattern that backtracks without end holds a request thread up to 5 s per string it checks before the data is refused (422). Only the application that declared the type can send such data, so it slows only its own requests, but on a shared thread pool. Options: reject nested quantifiers at declaration, validate on a bounded worker, or replace the pattern keyword handlers. | M8 (measured with the other request-path costs) |
| 7 | M2 confirmation | **False refusal:** the declaration dry run renders each template against empty data, so a template whose expression fails on a null operand (arithmetic or a typed function argument on `data.*`) is refused, though real data would render it. A static check of the template (names outside the sandbox's allowlist, `include`, `import`) instead of the dry run would refuse only what the sandbox forbids. | M5 (rendering) |
| 8 | M4 review, round 2 | **Race:** deleting a target (or its integration) checks that no route names it, but `PutRoute` checks the target exists at the same time, and `routes.targets` is a `text[]` with no foreign key, so a route can commit naming a target deleted at that moment. Locks taken in a handler don't help: Juice's `TransactionBehavior` opens the transaction after the handler runs. Fix: a `route_targets (tenant_id, route_id, target_id)` table with `ON DELETE RESTRICT` to `integration_targets`. Until then a route naming a missing target plans recipients that don't reach it; the delivery planner logs a warning naming the missing targets. | With configuration provisioning (I12), which rewrites how routes store targets anyway |
| 9 | M4 confirmation | **Hash drift:** a configuration row's definition hash is taken over canonical JSON, but the canonical writer keeps numbers as written while jsonb rewrites them (`1e2` is stored as `100`), so integration settings with such a number hash differently before and after a round trip through the database. Harmless today (the hash is a concurrency token compared against what was read); provisioning's drift check would see a false change. Fix: normalize numbers in `CanonicalJson`, or hash after the round trip. | With configuration provisioning (I12) |
